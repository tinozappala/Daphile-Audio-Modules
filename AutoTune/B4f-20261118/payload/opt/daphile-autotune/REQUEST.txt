## OBIETTIVO

Integrare nella nuova ISO Daphile attualmente in compilazione un modulo avanzato denominato provvisoriamente:

**Daphile AutoTune / Hardware-Aware Audio Optimization Engine**

Il modulo deve eseguire automaticamente:

- rilevamento completo dell'hardware;
- identificazione del DAC realmente utilizzato;
- identificazione della porta USB, hub, controller e percorso PCIe associati al DAC;
- analisi della topologia CPU;
- analisi ALSA e Squeezelite;
- analisi IRQ e interrupt;
- analisi dei servizi attivi;
- analisi dell'attività di sistema durante la riproduzione;
- individuazione di configurazioni potenzialmente subottimali;
- applicazione controllata di ottimizzazioni;
- benchmarking automatico;
- verifica della stabilità;
- generazione di profili;
- rollback automatico;
- comparazione A/B tra configurazioni.

L'obiettivo NON deve essere applicare indiscriminatamente generici "audiophile tweaks".

L'obiettivo deve essere invece costruire un sistema:

**hardware-aware, measurement-driven, conservative, reversible e self-validating.**

Ogni modifica deve essere applicata solo dopo aver identificato correttamente l'hardware e verificato che il relativo intervento sia tecnicamente appropriato.

---

# 1. PRINCIPI ARCHITETTURALI

Implementare AutoTune inizialmente come sottosistema il più possibile separato dal core Daphile.

Evitare, salvo reale necessità, modifiche invasive ai componenti fondamentali della distribuzione.

Preferire un'architettura del tipo:

```text
/opt/daphile-autotune/

    bin/
        dat-scan
        dat-cpu
        dat-usb
        dat-alsa
        dat-dac
        dat-irq
        dat-network
        dat-storage
        dat-services
        dat-runtime
        dat-benchmark
        dat-optimize
        dat-verify
        dat-profile
        dat-restore

    lib/
        detection/
        optimization/
        validation/
        profiles/

    rules/
        cpu.rules
        usb.rules
        alsa.rules
        irq.rules
        network.rules
        services.rules
        storage.rules

    profiles/
        default/
        safe/
        rt/
        low-activity/
        experimental/

    state/
        hardware.json
        baseline.json
        current.json
        last-known-good.json

    logs/
        autotune.log
        benchmark.log
        changes.log
```

L'architettura può essere modificata se tecnicamente opportuno, purché vengano mantenuti:

- modularità;
- reversibilità;
- tracciabilità;
- separazione detection/decision/action;
- possibilità di integrare successivamente il sistema nella GUI Daphile.

---

# 2. REGOLA FONDAMENTALE: ANALYZE BEFORE MODIFY

Nessuna ottimizzazione deve essere applicata senza che siano stati completati:

1. hardware discovery;
2. topology discovery;
3. DAC discovery;
4. USB path discovery;
5. ALSA analysis;
6. current Daphile/Squeezelite configuration analysis;
7. baseline capture.

Il flusso deve essere:

```text
SCAN
 ↓
ANALYZE
 ↓
CLASSIFY
 ↓
RECOMMEND
 ↓
SNAPSHOT
 ↓
APPLY
 ↓
TEST
 ↓
VERIFY
 ↓
COMMIT or ROLLBACK
```

Separare chiaramente:

```text
DETECTION
DECISION
ACTION
VALIDATION
```

# 3. HARDWARE DISCOVERY ENGINE

Creare una scansione completa del sistema utilizzando, quando disponibili:

```bash
lscpu
cat /proc/cpuinfo
lsusb
lsusb -t
lspci
lspci -nnk
aplay -l
aplay -L
cat /proc/asound/cards
cat /proc/interrupts
cat /proc/softirqs
find /sys/bus/usb/devices
find /sys/class/sound
find /sys/class/net
find /sys/devices/system/cpu
```

e le corrispondenti strutture `/sys`.

Il sistema deve rilevare almeno:

### CPU

- vendor;
- modello;
- architettura;
- numero CPU logiche;
- core fisici;
- thread per core;
- SMT/HyperThreading;
- NUMA se presente;
- governor disponibili;
- governor corrente;
- scaling driver;
- frequenza minima/massima;
- turbo/boost;
- C-state disponibili;
- clocksource;
- kernel utilizzato;
- eventuale kernel realtime/preempt;
- CPU affinity corrente;
- eventuali CPU isolate.

### Memoria

- RAM totale;
- RAM disponibile;
- swap;
- hugepages se rilevanti;
- eventuali anomalie di memoria.

### PCIe

- controller USB;
- controller SATA/NVMe;
- NIC;
- audio HDMI;
- Wi-Fi;
- Bluetooth;
- altri controller rilevanti.

### Storage

- dispositivi;
- filesystem;
- mount;
- supporti locali;
- supporti di sistema;
- supporti contenenti libreria musicale, se identificabili.

### Network

- interfaccia utilizzata;
- driver;
- velocità;
- duplex;
- offloading;
- interrupt;
- eventuali interfacce inutilizzate.

# 4. DAC DISCOVERY

Il modulo deve identificare automaticamente il DAC effettivamente configurato/utilizzato da Daphile/Squeezelite.

Non limitarsi a rilevare tutti i dispositivi ALSA.

Determinare:

```text
DAC selezionato da Daphile
        ↓
ALSA card
        ↓
ALSA PCM device
        ↓
USB device
        ↓
USB port
        ↓
USB hub
        ↓
root hub
        ↓
USB controller
        ↓
PCI device
        ↓
IRQ
```

Generare una struttura simile:

```json
{
  "dac": {
    "name": "Aqua La Scala MKII Optologic",
    "alsa_card": 2,
    "alsa_device": 0,
    "vid": "xxxx",
    "pid": "xxxx",
    "usb_speed": "480M",
    "usb_path": "3-2",
    "root_hub": "usb3",
    "controller": "0000:00:14.0",
    "irq": 124
  }
}
```

L'identificazione deve essere robusta anche dopo reboot.

Usare, quando disponibili:

- VID;
- PID;
- serial number;
- ALSA ID;
- USB physical path;
- product string.

Non affidarsi esclusivamente al numero statico `hw:X,Y`, poiché può cambiare.

# 5. USB TOPOLOGY ANALYSIS

Ricostruire l'intera topologia USB.

Per ogni porta/controller determinare:

- USB version;
- negotiated speed;
- root hub;
- hub intermedi;
- dispositivi condivisi;
- controller;
- PCI address;
- IRQ;
- driver;
- autosuspend;
- runtime PM;
- eventuali errori/reset osservabili.

Per la porta utilizzata dal DAC produrre un report:

```text
DAC USB PATH

Aqua La Scala
    └── USB 2.0 High-Speed
        └── Port 3-2
            └── Root Hub usb3
                └── xHCI controller
                    └── PCI 0000:00:14.0
                        └── IRQ 124
```

# 6. USB PORT ANALYZER

Implementare un sistema capace di valutare le porte USB disponibili.

Il punteggio deve essere basato esclusivamente su parametri tecnicamente osservabili.

Valutare per esempio:

- controller dedicato/condiviso;
- root hub condiviso;
- numero di periferiche concorrenti;
- presenza Wi-Fi/Bluetooth sullo stesso controller;
- IRQ condivisi;
- traffico osservato;
- errori;
- reset;
- runtime power management;
- USB speed.

Esempio:

```text
USB PORT ANALYSIS

Port A
Controller shared
Wi-Fi present
IRQ shared
Score: 61

Port B
Dedicated root hub
No competing devices
Independent IRQ
Score: 94

Port C
Internal hub
Multiple devices
Score: 70
```

Fornire una raccomandazione:

```text
RECOMMENDED DAC USB PORT: PORT B
```

IMPORTANTE:

Non dichiarare che una porta "suona meglio".

Definire il punteggio esclusivamente come:

**USB topology / isolation / activity score.**

# 13. CPU AFFINITY ENGINE

Esempio concettuale:


# 16. CPU GOVERNOR

Analizzare il governor esistente.

NON assumere:

```text
performance = migliore audio
```

Supportare strategie differenti:

### SAFE

Mantenere comportamento più vicino possibile al sistema originale.

### AUDIO-RT

Favorire scheduling prevedibile.

### LOW-ACTIVITY

Favorire riduzione dell'attività di sistema e dei wakeup.

### EXPERIMENTAL

Consentire impostazioni più aggressive.

Registrare sempre:

```text
before
after
reason
```

# 25. SAFE AUTOTUNE

`SAFE AUTOTUNE` può includere, dopo verifica:

- DAC USB autosuspend disable;
- corretto device ALSA;
- Squeezelite realtime scheduling;
- buffer tuning conservativo;
- sospensione di hardware wireless inutilizzato;
- disabilitazione di audio devices inutilizzati;
- correzione affinity palesemente errata;
- ottimizzazione non distruttiva.

Non deve modificare:

- BIOS;
- firmware;
- filesystem;
- partition table;
- bootloader;

salvo futura implementazione esplicita e separata.

---

# 26. ADVANCED AUTOTUNE

Può includere:

- CPU affinity;
- IRQ affinity;
- governor;
- selected C-state policy;
- clocksource testing;
- service isolation;
- CPU core isolation;
- advanced USB power management.

Tutte le modifiche devono essere reversibili.

---

# 27. EXPERIMENTAL MODE

Inserire qui:

- aggressive C-state restrictions;
- fixed CPU frequency;
- extreme IRQ isolation;
- isolcpus/nohz_full/rcu_nocbs se tecnicamente compatibili;
- alternative clocksource;
- aggressive VM parameters;
- advanced USB controller tuning;
- service shutdown aggressivo.

Richiedere conferma esplicita prima dell'applicazione.

# 29. EVIDENCE CLASSIFICATION

Distinguere esplicitamente:

### OBJECTIVELY MEASURABLE

- XRUN;
- underrun;
- CPU latency;
- wakeup;
- IRQ;
- reset;
- error;
- load;
- activity.

### ENGINEERING ASSUMPTION

Ottimizzazione plausibile ma senza prova diretta di miglioramento sonoro.

### EXPERIMENTAL/AUDIOPHILE

Tweak non dimostrabile direttamente via software.

Il sistema NON deve mai trasformare una correlazione tecnica in una falsa dichiarazione del tipo:

```text
sound quality improved by 17%
```

Questo deve essere vietato.

# 32. TRANSACTIONAL CHANGES

Ogni ciclo di tuning deve funzionare come una transazione:

```text
BEGIN
SNAPSHOT
APPLY
TEST
VERIFY

if PASS:
    COMMIT

if FAIL:
    ROLLBACK
```

Nessuna modifica deve essere considerata valida finché la verifica non è terminata.

# 34. BOOT FAILURE RECOVERY

Valutare l'implementazione di un meccanismo:

```text
Boot with AutoTune profile
        ↓

        ↓
```
